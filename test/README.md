# test —— TCP 回显服务器 QPS 压测客户端

两个用 C 写的 TCP 回显（echo）服务器压测客户端，主要用于给
[`netio/io_uring/echo_server`](../netio/io_uring/) 做 **QPS / RTT / 吞吐**测试，
也可以压任何“收到多少字节就原样回显多少字节”的 TCP 服务。

| 文件 | 版本 | 定位 | 适用场景 |
|------|------|------|---------|
| [`test_qps_tcpclient.c`](test_qps_tcpclient.c) | v1 | 简单版：一线程一连接，同步“发一包、收一包” | 冒烟测试、和 v2 对照 |
| [`test_qps_tcpclient_v2.c`](test_qps_tcpclient_v2.c) | v2 | 完整版：多线程 × 多连接 × pipeline，应用层分帧 | 正式压测、验证拆包/粘包 |

> **平台**：仅 Linux / WSL2。代码依赖 POSIX socket、`pthread`、`poll`、`getopt`，
> Windows 原生 MSVC 无法编译；被测的 `io_uring` 回显服务器本身也只在 Linux 下可用。

---

## 1. 被测对象的行为约束

压测结果是否可信，取决于是否理解服务端的实现。`netio/io_uring/echo_server.c` 的关键约束：

| 项 | 值 | 对压测的影响 |
|----|----|-------------|
| 接收/发送缓冲区 | `BUFF_SIZE = 4096` | 一次 `recv` 最多读 4096 字节；大于 4096 的请求必然被拆成多次回显 |
| 连接表容量 | `MAX_CONNS = 1024`，fd 直接作为数组下标 | 客户端总连接数建议 ≤ 900（还要扣除 stdin/stdout/stderr/listen fd） |
| 监听队列 | `LISTEN_BACKLOG = 128` | 瞬间大量 `connect` 可能失败，客户端需要容忍连接失败 |
| 每连接在途操作 | 同一时刻只有 1 个（`recv → send → recv` 串行） | 客户端 pipeline 只能隐藏网络 RTT，服务端回显仍是串行的 |
| 回显语义 | 收到多少字节就回多少字节 | 客户端必须自己按字节流做应用层分帧 |
| 调试输出 | 每次 `recv` 都 `fprintf` + `fwrite` 到 stdout | 压测时必须重定向到 `/dev/null`，否则测到的是终端 I/O 速度 |
| `TCP_NODELAY` | 服务端未设置 | Nagle + 延迟 ACK 可能让少量小包 RTT 出现毫秒级抖动 |

两个客户端都只支持 **IPv4**。

两个源文件都是单文件程序，用 gcc 直接编译：

```bash
cd cpp_internet_study/test

# v2（推荐）：需要 pthread 和 GNU 扩展
gcc -O2 -Wall -Wextra -D_GNU_SOURCE -pthread \
    test_qps_tcpclient_v2.c -o test_qps_tcpclient_v2

gcc -O2 -Wall -Wextra -pthread \
    test_qps_tcpclient.c -o test_qps_tcpclient
```

也可以只编译 v2，v1 仅在需要对照时使用。

## 4. v1：简单版客户端 `test_qps_tcpclient.c`

### 4.1 工作模型

```
main
 ├─ 解析 -s / -p / -t / -c / -n
 ├─ 记录开始时间
 ├─ 创建 T 个线程
 │    └─ test_qps_entry
 │         ├─ connect_tcpserver()：每个线程建 1 条连接
 │         └─ 循环 n / T 次：
 │              send_recv_tcppkt()
 │                ├─ 把 64 字节模板重复 30 次 → 1920 字节
 │                ├─ send() 一次
 │                ├─ recv() 一次到 2048 字节缓冲区
 │                └─ strcmp() 比较回显内容
 ├─ join 所有线程
 └─ 统计：成功数、失败数、总耗时、QPS
```

### 4.2 代码内容

| 函数 | 职责 |
|------|------|
| `connect_tcpserver()` | `socket()` + `connect()`，失败返回 -1 |
| `send_recv_tcppkt()` | 构造请求、`send()`、单次 `recv()`、`strcmp()` 校验 |
| `test_qps_entry()` | 线程入口：建一条连接，按 `n / t` 循环发送请求 |
| `main()` | 解析参数、创建/回收线程、计时并打印 QPS |

每次请求的报文固定为 **1920 字节**：`TEST_MESSAGE` 是 64 字节的可见字符模板
（字母 + 数字 + `\r\n`），重复 30 次。比默认的小包更大，用来观察服务端在较大
报文下的回显表现。

### 4.3 参数

| 参数 | 含义 | 默认值 | 说明 |
|------|------|--------|------|
| `-s` | 服务器 IP | 无 | 必须指定；只支持 IPv4，内部用 `char[16]` 保存 |
| `-p` | 服务器端口 | 无 | 必须指定 |
| `-t` | 线程数 | 无 | 必须指定且 > 0；每个线程一条连接 |
| `-c` | 连接数 | 无 | **解析了但未使用**，历史遗留参数 |
| `-n` | 总请求数 | 无 | 必须指定；每个线程分到 `n / t` 次 |

### 4.4 输出

```text
success conns = 100000, failed conns = 0, timeused = 1234, qps = 81037
```

- `success conns` / `failed conns`：实际是**请求数**，字段名沿用旧代码，容易误解。
- `timeused`：毫秒。
- `qps`：`requestion * 1000 / timeused`，分母是**请求总数**而不是成功数，
  且计时包含线程创建和 `connect` 的时间。

### 4.5 已知局限

v1 的定位是“能跑起来的冒烟客户端”，不适合做严谨压测：

| 局限 | 后果 |
|------|------|
| 每个线程只建 1 条连接 | 无法测“大量并发连接”场景 |
| `-c` 不生效 | 参数与行为不一致 |
| 请求后只调用一次 `recv()` | 字节数超过一次 `recv` 或 TCP 拆包时会误判失败 |
| 没有应用层分帧 | 依赖“服务端一次回显完整”的隐含假设 |
| 不处理 `send` 短写 | 大报文或发送缓冲区满时可能少发 |
| 计时包含 `connect` | 连接建立耗时计入 QPS |
| 请求数按 `n / t` 整数均分 | 余数请求被静默丢弃，但 QPS 仍用 `-n` 作分子 |
| `ctx->failed++` 无原子保护 | 多线程下失败计数存在数据竞争 |
| 校验失败不影响退出码 | `strcmp` 不匹配只累加 `failed`，正常跑完 `main` 仍返回 0；只有 `send` / `recv` 错误才 `exit(1)` |
| 失败计数 ≠ 实际完成数 | 线程遇到失败立即返回，未执行的请求仍被算进 `success conns`（`n - failed`） |
| `send` / `recv` 失败直接 `exit(1)` | 任意一个线程出错会杀掉整个进程 |
| 无默认值和参数校验 | 不传 `-t` / `-n` 可能除零；不传 `-s` 会连到错误地址 |

> 结论：v1 适合确认“服务器能通、大致有多快”；
> 需要准确数字或验证拆包/粘包时，用 v2。

## 5. v2：完整版客户端 `test_qps_tcpclient_v2.c`

v2 是真正用于压测的版本，解决了 v1 的全部上述问题。

### 5.1 工作模型

```
main
 ├─ 解析参数、校验、生成 payload 模板
 ├─ 建立 T 个 worker，把 C 条连接和 N 个请求尽量均分
 ├─ pthread_create × T
 │    └─ worker_entry
 │         ├─ 顺序建立本线程负责的连接（非阻塞 connect + 3 秒超时）
 │         ├─ pthread_barrier_wait   ← 所有线程连接就绪后才放行
 │         ├─ 开始计时
 │         ├─ worker_run：poll 事件循环
 │         │    ├─ 按需 conn_queue() 填充新帧（在途 ≤ pipeline）
 │         │    ├─ POLLOUT → conn_flush()：send，处理短写 / EAGAIN
 │         │    ├─ POLLIN  → conn_recv() → conn_parse()：拆包 / 粘包
 │         │    └─ 60 秒无任何完整响应则判定停滞并退出
 │         └─ 结束计时
 └─ pthread_join × T → 汇总全局统计和每线程统计
```

关键点：**连接建立放在 barrier 之前**，所有线程把连接建好后才一起开始发请求，
因此 `connect` 耗时不会进入 QPS 统计。

### 5.2 应用层帧格式

TCP 是字节流，`send` 的边界和 `recv` 的边界没有对应关系。为了让客户端能判断
“一个请求是否完整回来”，v2 在 payload 前加了 12 字节帧头（网络字节序，大端）：

```text
 0        4        8        12                        12+len
 +--------+--------+--------+--------------------------+
 | magic  |  seq   |  len   |        payload           |
 | 4B     | 4B     | 4B     |        len 字节           |
 +--------+--------+--------+--------------------------+
```

| 字段 | 值 | 作用 |
|------|----|------|
| `magic` | `0x51505431`（`"QPT1"`） | 快速识别流是否错位 |
| `seq` | 每连接从 0 递增 | 校验响应顺序、计算 RTT 下标 |
| `len` | 固定等于 `-b` | 校验分帧和缓冲区边界 |
| `payload` 前 4 字节 | 再次写入 `seq` | 防止“帧头对、内容错” |
| `payload` 其余字节 | 固定模板 `(i * 131 + 17) & 0xff` | 逐字节校验回显内容 |

一帧总大小 = `12 + payload`。默认 payload 64 字节，即一帧 76 字节。

### 5.3 参数

| 参数 | 含义 | 默认值 | 合法范围 / 约束 |
|------|------|--------|----------------|
| `-s` | 服务器 IPv4 地址 | `127.0.0.1` | 用 `inet_pton` 校验 |
| `-p` | 服务器端口 | `9999` | 1..65535 |
| `-t` | 工作线程数 | `1` | 1..256（`MAX_WORKERS`） |
| `-c` | 总连接数 | 等于 `-t` | 必须 ≥ `-t` |
| `-n` | 总请求数 | `10000` | 必须 ≥ `-c` |
| `-b` | 每帧 payload 字节数 | `64` | 4..16 MiB（前 4 字节要放 seq） |
| `-P` | 每连接最大在途请求数（pipeline） | `1` | 1..64 |
| `-h` | 打印用法 | — | — |

程序启动时会做以下保护：

- `-c > 1000` 时打印警告（服务端 `MAX_CONNS = 1024`）。
- 估算客户端缓冲区超过 4 GiB 时直接拒绝启动，避免 `-b 16M -P 64 -c 1000`
  这类组合把机器内存打爆。
- 每连接内存约为：发送队列 `P × (12 + b)` + 接收缓冲 `(12 + b) + 4096`
  + RTT 数组 `P × 8`。

### 5.4 代码内容

| 结构 / 函数 | 职责 |
|-------------|------|
| `config_t` | 全局配置（ip/port/threads/conns/requests/payload/pipeline），解析后只读 |
| `conn_t` | 单连接状态：fd、发送队列、接收累积缓冲区、序号、在途计数、目标数、RTT 时间戳环 |
| `worker_t` | 单线程状态：连接数组、`pollfd` 数组、统计、起止时间 |
| `tcp_connect()` | 非阻塞 `connect` + `poll` 3 秒超时 + `SO_ERROR` 检查，并设置 `TCP_NODELAY` |
| `build_frame()` | 构造 `magic + seq + len + payload` 帧 |
| `conn_init()` | 分配每连接缓冲区、按全局序号均分请求数、初始化 RTT 环 |
| `conn_flush()` | 循环 `send`，处理短写、`EINTR`、`EAGAIN`；发完重置队列 |
| `conn_parse()` | 从接收缓冲区循环解析完整帧，校验 magic/len/seq/payload，计算 RTT，`memmove` 压缩残留半帧 |
| `conn_recv()` | 单次事件最多循环 32 次 `recv`，处理 EOF、`EAGAIN`、错误，避免饿死同线程其他连接 |
| `conn_queue()` | 仅在发送队列为空时追加新帧，在途数不超过 pipeline |
| `conn_fail()` | 记录连接级错误、关闭 fd、标记连接结束（每个线程最多打印 5 条错误） |
| `worker_run()` | 单线程 `poll` 事件循环，负责排队、收、发、停滞检测和收尾 |
| `worker_entry()` | 线程入口：建连接（连续失败 5 次则跳过剩余连接）→ barrier → 计时 → 运行 |
| `main()` | 解析参数、校验、生成模板、分配 worker、创建线程、汇总并打印结果 |

### 5.5 实现要点

1. **非阻塞 connect + 超时**
   `connect()` 返回 `EINPROGRESS` 后用 `poll(POLLOUT)` 等待，最长 3 秒；
   超时或 `SO_ERROR` 非零则失败。服务器没启动时，连续失败 5 次会跳过本线程
   剩余连接，避免每个连接都等满 3 秒。

2. **统一计时起点**
   `pthread_barrier_t` 的计数是 `线程数 + 1`：worker 建完连接后等待，main
   也等待；所有连接就绪后同时放行，之后才开始计时。

3. **短写处理**
   发送队列用 `slen`（已排入字节数）和 `soff`（已发出字节数）两个游标；
   `send` 返回正数就推进 `soff`，`EAGAIN` 就等下一次 `POLLOUT`，
   全部发完才重置队列。只有队列为空时才追加新帧，保证不会在帧中间插入数据。

4. **拆包 / 粘包**
   - 拆包：`rlen - off < need` 时 `break`，半帧留在缓冲区，等下一次 `recv` 补齐。
   - 粘包：`while` 循环一次消费多帧。
   - 一次解析后如果还有残留，用一次 `memmove` 把残留移到缓冲区头部，避免逐帧搬移。
   - 每线程统计 `partial_waits`（需要等下一次 `recv` 的次数）和
     `max_batch`（单次解析出的最大整帧数），用来证明两条路径确实被触发。

5. **在途请求与 RTT**
   在途帧数不超过 pipeline，响应又必须按序返回，因此
   `seq % pipeline` 可以安全地作为 RTT 时间戳环下标，不会覆盖尚未返回的帧。
   时间戳在“帧进入发送队列”时记录，所以 `-P > 1` 的 RTT 包含排队时间，
   会略大于纯网络往返时间。

6. **错误处理**
   - `SIGPIPE` 忽略，`send` 使用 `MSG_NOSIGNAL`。
   - `recv` 返回 0 表示对端关闭：如果目标已完成算成功，否则算连接异常。
   - `magic` / `len` / `seq` / `payload` 任何一项不匹配都按协议错误断开该连接。
   - 60 秒没有收到任何完整响应帧就终止，防止服务端卡死时客户端永久挂住。

7. **成功判定**
   只有“序号连续 + 长度正确 + payload 前 4 字节序号正确 + 其余字节与模板逐字节一致”
   的响应才计入 `ok`；QPS 只统计成功响应。

### 5.6 输出与指标

```text
==================== 压测配置 ====================
服务器            : 127.0.0.1:9999
线程 / 连接       : 4 / 64
请求总数          : 200000（每连接约 3125）
payload / 帧大小  : 1920 / 1932 字节
每连接 pipeline   : 4
客户端缓冲估算    : ... MiB（所有连接发送队列 + 接收缓冲）
连接建立耗时不参与统计；成功判定 = 序号 + 长度 + 内容全部匹配
==================================================

==================== 压测结果 ====================
目标请求数        : 200000
成功响应          : 200000
失败 / 未完成     : 0
连接失败/异常     : 0
半帧等待次数      : ...（>0 可确认发生过拆包；次数≠帧数）
单次最多整帧数    : ...（>1 可确认发生过粘包）
耗时              : ... 秒
QPS               : ... 次/秒
吞吐              : ... MiB/s（收发合计）
RTT 平均/最小/最大: ... / ... / ... us

---------------- 每线程统计 ----------------
thread 0   连接=16   目标=50000   成功=50000   失败=0   错误=0   QPS=...
...
==================================================
```

> 具体数值因机器、内核、服务端是否重定向 stdout 等因素而变，上面只展示字段格式。

| 指标 | 含义 |
|------|------|
| 目标请求数 | 所有连接分配到的请求数之和，正常情况下等于 `-n` |
| 成功响应 | 通过全部校验的响应帧数 |
| 失败 / 未完成 | `目标请求数 - 成功响应`，包含连接失败导致的未发请求 |
| 连接失败/异常 | 连接建立失败、连接中途异常、收尾时未完成目标的连接次数 |
| 半帧等待次数 | 解析时遇到残留字节、需要等下一次 `recv` 的次数；**次数不是被拆的帧数** |
| 单次最多整帧数 | 一次 `conn_parse` 连续解析出的最大完整帧数；>1 说明观察到了粘包 |
| 耗时 | 所有 worker 中最早开始到最晚结束的时间 |
| QPS | `成功响应数 / 耗时` |
| 吞吐 | `成功响应数 × 帧大小 × 2 / 耗时`，收发两个方向都计入 |
| RTT 平均/最小/最大 | 从帧进入发送队列到收到对应响应的微秒数 |

退出码：全部请求成功返回 `0`；存在失败/未完成返回 `1`。

### 5.7 复现拆包与粘包

```bash
# 服务器保持：./echo_server > /dev/null

# 拆包：请求帧 8204 字节，远大于服务端 4096 的 recv 缓冲区
./test_qps_tcpclient_v2 -s 127.0.0.1 -p 9999 \
    -t 2 -c 16 -n 20000 -b 8192 -P 16
```

运行结束后应看到：

- `半帧等待次数 > 0`：服务端一次只能读 4096 字节，一帧必然跨多次回显，
  客户端必须缓存半帧等待补齐。
- `单次最多整帧数 > 1`：客户端一次连发多帧，服务端一次 `recv` 可能读到多帧
  并一起回显，客户端一次解析出多帧。

这两个计数是“本次运行观察到了该现象”的证据；反过来为 0 并不代表 TCP 不拆包，
只代表这次没有触发。

## 6. 压测建议

1. **重定向服务端 stdout**
   `echo_server` 每收到一段数据都会 `fwrite` 并 `fflush`，不重定向时终端 I/O
   会成为瓶颈，测出来的不是网络栈性能：
   ```bash
   ./echo_server > /dev/null
   ```

2. **连接数留余量**
   服务端 `MAX_CONNS = 1024` 且 fd 直接做数组下标，客户端总连接数建议 ≤ 900。

3. **分级测试**
   ```bash
   # 基线：单线程单连接，测最低 RTT
   ./test_qps_tcpclient_v2 -s 127.0.0.1 -p 9999 -t 1 -c 1 -n 100000 -b 64 -P 1

   # 并发：多线程多连接，测服务端吞吐上限
   ./test_qps_tcpclient_v2 -s 127.0.0.1 -p 9999 -t 4 -c 64 -n 200000 -b 1920 -P 4

   # 管道：每连接多个在途请求，隐藏 RTT
   ./test_qps_tcpclient_v2 -s 127.0.0.1 -p 9999 -t 4 -c 64 -n 200000 -b 64 -P 16
   ```

4. **客户端与服务端不要抢同一个 CPU**
   本机测试时可用 `taskset` 把服务端和客户端绑到不同核，减少调度噪声。

5. **注意 pipeline 对 RTT 的影响**
   `-P > 1` 时 RTT 包含发送排队时间；想看纯网络往返，用 `-P 1`。

6. **服务端 Nagle**
   服务端没有设置 `TCP_NODELAY`，小包场景可能出现毫秒级 RTT 抖动，这是服务端
   行为，不是客户端统计错误。客户端自己设置了 `TCP_NODELAY`，避免客户端侧的
   Nagle 干扰。

## 7. 常见问题

| 现象 | 可能原因 | 处理 |
|------|---------|------|
| 大量“失败 / 未完成”且“连接失败/异常” > 0 | 服务端没启动、端口不对、`MAX_CONNS` / backlog 限制 | 先确认 `echo_server` 在监听；把 `-c` 降到 900 以内 |
| 连接每个都卡 3 秒 | 服务端不可达，非阻塞 connect 等满超时 | v2 连续失败 5 次会跳过剩余连接，先修服务端 |
| QPS 明显偏低 | 服务端 stdout 没重定向 | `./echo_server > /dev/null` |
| `半帧等待次数 = 0` | payload 太小或发送/接收节奏刚好对齐 | 用 `-b 8192` 并让服务端 `BUFF_SIZE=4096` 强制拆包 |
| `单次最多整帧数 = 1` | 本次运行没有观察到粘包 | 增大 `-P` / payload，或多跑几轮；计数为 0 不代表不会发生 |
| RTT 偶发毫秒级 | 服务端 Nagle + 延迟 ACK、CPU 调度 | 属正常现象；需要更稳定数据可多轮取统计 |
| `connect: Connection refused` | 端口没有服务端监听 | 启动 `echo_server` 或检查 `-p` |
| `io_uring_queue_init: Operation not permitted` | 容器 / WSL 的 seccomp 禁用了 io_uring | 换真实 Linux 虚拟机或放宽 seccomp |
| 程序 60 秒后自行退出 | 服务端卡死或协议不匹配，客户端停滞保护触发 | 检查服务端是否真的按字节回显 |
| 编译报 `pthread_barrier_*` 未定义 | 没加 `-pthread` 或 `-D_GNU_SOURCE` | 按第 2 节命令重新编译 |
| 内存不足 / 被拒绝启动 | `-b`、`-P`、`-c` 组合太大 | 减小参数；程序会拒绝估算超过 4 GiB 的配置 |

## 8. 与仓库其他部分的关系

- 被测服务端：[`netio/io_uring/echo_server.c`](../netio/io_uring/echo_server.c)，
  其 one-shot accept/recv/send 模型见
  [`netio/io_uring/README.md`](../netio/io_uring/README.md)。
- v2 的“帧头 + 长度前缀”思路与 `multi_io` 的 HTTP 增量解析、`udp_kcp` 的
  KCP 报文分帧属于同一类问题：**TCP 是字节流，协议边界必须由应用层自己定义**。
- 服务端每条连接同一时刻只有一个在途操作，因此 v2 的 pipeline 只能隐藏网络
  RTT，不能提高服务端单连接的回显并行度；要提升服务端吞吐，需要改服务端
  （多连接、multishot、provided buffer 等，见 io_uring README 第 8 节）。
